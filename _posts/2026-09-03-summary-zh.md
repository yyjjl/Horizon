### [Paint.NET 用 Claude 为 Wine 净室重写 Direct2D](https://simonwillison.net/2026/Sep/2/rick-brewster/) ⭐️ 8.0/10

Paint.NET 作者 Rick Brewster 表示，该应用现在内置了一套自研、从零开始的净室逆向工程重写版 Direct2D，专门在 Wine 上通过 /wine 参数启用，代码位于 PaintDotNet.Windows.Direct2D1.Managed.dll 中。这套约 18 万行的实现主要由 Claude 生成，Brewster 称大部分代码属于未经彻底审查的“vibe coding”，他自己不可能逐行审阅这么多代码，作为对比整个 Paint.NET 约 70 万行代码由他维护了 20 多年。Claude 在过程中有时表现惊人，能逆向推导 Direct2D 内置效果库所需公式，但也曾漏掉 COM 引用计数 AddRef 的资源管理操作，需要人工持续监督。该改动直接绕过了 Wine 对 Direct2D 支持长期不足、难以满足 Paint.NET 需求的瓶颈，是 AI 辅助软件工程在兼容层逆向工程上一个值得关注的实验性案例，但官方明确标注为“极度实验性”，代码尚未被充分审查。

rss · Simon Willison · 9月2日 05:50

**「背景」** Direct2D 是微软的 Windows 2D 图形 API；Paint.NET 依赖它，若 Wine（让 Windows 程序在 Linux 等系统上运行的兼容层）未完整实现该 API，程序就无法正常渲染。净室逆向工程指在不复制原实现代码的前提下，依据公开接口和行为规范独立重写兼容实现。Brewster 认为 Wine 的 Direct2D 永远不可能完善到满足 Paint.NET 需要，因此改用 Claude 帮助生成内部替代实现来规避这一障碍。

**「影响」** 该成果最直接的后果是，在 Wine/Linux 上运行 Paint.NET 的用户现在可以用 /wine 参数触发这套独立 Direct2D 实现，获得一条实验性的兼容路径；不过由于 Brewster 明说大部分代码“trust me bro”、未经充分审阅并需要人工照看，它不能被视为生产级稳定方案。

rss · NVIDIA Developer Blog · 9月2日 17:15

### [编码智能体支撑系统源代码解剖：从工具到平台](https://arxiv.org/abs/2609.00006) ⭐️ 8.0/10

arXiv 论文 2609.00006 对 11 个生产级编码智能体支撑系统（Claude Code、Codex CLI、Gemini CLI、Mistral Vibe、OpenHands、Aider、Mini-SWE-Agent、Hermes、Pi、OpenCode、OpenClaw）以及首个元支撑系统 Omnigent 进行了源代码解剖。研究定义了支撑系统（harness）为模型加运行时的结构，绘制了七个规范子系统，并在约 400 万行 Python、TypeScript 和 Rust 代码中总结出 13 项跨系统观察和 29 个反复出现的设计模式。关键发现是：没有代理运行时导入通用智能体框架，也没有系统使用向量嵌入检索代码；SKILL.md 技能在 11 个系统中的 9 个中得到采用，超过 MCP 的 8 个；ACP 出现在 6 个系统中，并引入“支撑系统承载”这一第三种角色。由于原始 8 个系统被重新固定而非替换，研究还提供了跨一个季度的受控纵向差异样本，显示系统间趋同正变成模仿，行为策略正从提示文字迁移到配置。论文的论点是：2026 年上半年，编码支撑系统完成了从工具到平台的转变，并附有 18 条设计建议和一个 90 行的最小可行支撑系统脚手架。

rss · arXiv cs.MA · 9月2日 04:00

**「背景」** 智能体可看作“模型加支撑系统”，其中支撑系统是指通过循环、工具、上下文管理、安全控制、编排和扩展接口将大语言模型连接到外部世界的运行时。支撑系统工程（harness engineering）于 2026 年初被命名，旨在设计和演进这类运行时，但此前缺少系统的经验基础；这篇论文正是针对这一新兴学科的第一份全面实证研究。

**「影响」** 对于从事智能体运行时构建的工程师而言，这项研究提供了最完整的生产级支撑系统架构图谱，使团队可以围绕明确的子系统、模式及反模式展开设计，并依据经验证据判断自研运行时与通用框架、向量检索之间的取舍。

### [用 MD5 逐步计算评测大模型的长程状态跟踪能力](https://arxiv.org/abs/2609.00012) ⭐️ 8.0/10

这篇 arXiv 预印本提出一项评测基准，要求大语言模型在 196 次相互依赖的工具调用中逐步计算 MD5 哈希，以单独检验其长程状态跟踪能力。该任务包含 64 轮计算，模型须在上下文中跨调用携带 a、b、c、d 四个 32 位字，并采用从零实现的 RFC 1321 MD5，使每次调用都能与基准轨迹逐位比对。结果显示，gpt-oss-120b（每 token 约 55 亿激活参数的混合专家模型）在温度为 0、短固定提示下，能在多数完成运行中跨全部 196 次调用保持状态并返回正确摘要。研究还发现，两个不改变权重的因素决定成败：每轮保留模型自身推理过程，以及对启用思考的 worker 进行投票以消除模运算错误。该方法还将剩余失败按来源区分，分离出状态携带、算术运算和推理服务三类问题。

rss · arXiv cs.MA · 9月2日 04:00

**「背景」** 长程智能体任务中，模型需要在多次工具调用之间持续携带并更新中间状态，但已有评测常将状态跟踪失败与指令理解、算术误差混在一起，且模型可能通过编造最终答案绕过真正计算。该论文用 MD5 哈希构造一个标准任务：模型要经历 196 次依赖前一步的工具调用、在上下文中维护四个 32 位状态字，并把每次调用与 RFC 1321 的参考实现逐位对照，从而单独度量“状态簿记”能力。第一作者 Dheeraj Mohandas Pai 来自卡内基梅隆大学；arXiv 上另有相关研究（如 2511.10457、2503.02854）也在探讨语言模型的状态跟踪机制，可作为理解该工作的背景。

**「影响」** 该基准为研究者提供了一种可复现、能区分长程 agent 失败来源的评估工具，有助于针对状态携带缺陷改进模型或推理流程，而不是被整体端到端成功率掩盖问题。

### [GlossoGen：LLM 智能体会涌现出人类看不懂的组合语言](https://arxiv.org/abs/2609.01491) ⭐️ 8.0/10

一项研究提出 GlossoGen 平台，用于在复杂多智能体 LLM 场景中研究语言演化，并构建了 SaveVeyru 场景，让拥有部分信息的智能体在压力下通信。结果显示，LLM 智能体之间会发生语言演化，产生的语言具有组合性和形态能产性，且偏离其英语先验，使人类难以理解。研究识别了几种促成演化的关键条件：效率压力、支撑智能体的模型强度，以及允许智能体商定语言约定的“事后复盘”（postmortem）阶段。研究还发现，新智能体可以仅通过使用学会已有语言并主动参与学习；较强模型是新型语言涌现所需，而较弱模型也能在语言出现后习得该语言。作者据此认为当前 LLM 具备此前仅在人类身上证实的累积文化演化潜力，混合智能体群体的能力可能超越其中最低能力的个体。

rss · arXiv cs.MA · 9月2日 04:00

**「背景」** 语言演化通常指语言在传播过程中形成系统性结构和约定，而组合性、能产性等特征被视为人类语言的重要标志。此前，累积文化演化主要在人类社会中被证实，但随着 LLM 驱动的智能体越来越多地自动互动，研究者开始关注这类系统中是否也会出现类似的语言形成过程。GlossoGen 正是为在可控、复杂场景中观察这一现象而设计的研究平台。

**「影响」** 该项工作对部署多智能体 LLM 系统的开发者和运营者有直接警示意义：代理可能自发形成高效但人类无法监控的通信约定，削弱安全审计和可解释性；同时，强弱模型混用时群体整体能力可能超出最低能力个体，这会影响系统设计和能力评估。

### [美司法部支持 AI 训练为合理使用，介入纽约时报案](https://the-decoder.com/us-department-of-justice-backs-fair-use-for-ai-training-in-landmark-copyright-case/) ⭐️ 8.0/10

美国司法部在《纽约时报》诉 OpenAI 和微软的合并版权诉讼中表态支持 AI 公司，主张用受版权保护的作品训练 AI 模型属于合理使用，不构成版权侵权。司法部认为训练时虽然复制了完整作品，但复制从未公开，且模型输出“经常（如果不是总是）”与原始作品缺乏实质性相似，因此不能把训练与输出混为一谈。该意见引述琼·狄迪恩抄写海明威作品学习写作的类比，并称人类利用大型语言模型创作原创作品，若仅因训练就施加版权责任会扼杀版权法本应保护的创造力。司法部还直接反驳美国版权局此前拒绝普遍适用合理使用的报告，称其无约束力且忽视了逐案分析和法定市场损害标准。此案自 2023 年底纽约时报起诉以来被视为 AI 训练版权纠纷的风向标。

rss · The Decoder · 9月2日 18:24

**「背景」** 合理使用是美国版权法允许未经许可使用受保护作品的情形，需按具体目的、性质、数量和市场影响等因素逐案判断。纽约时报等权利人起诉 OpenAI 与微软，称数十万篇文章被用来训练 GPT-4 等模型并构成竞争性信息产品；司法部此次立场与版权局此前明确不承认 AI 训练普遍属于合理使用的结论相左。

**「影响」** 由于本案被视为判断 AI 训练是否合理使用的标杆案件，其判决将直接影响 OpenAI、微软及其他 AI 公司能否不经授权使用大规模版权内容，也关系到已训练模型的存续；现阶段的政府意见并不等于最终裁判。

NVIDIA 发布博客，介绍如何通过投机解码与模型协同设计加速 LLM 推理并保持准确性，提出五条选择草稿长度和草稿机制的准则。投机解码由小型草稿模型一次预测多个 token，再由目标模型并行验证，保留被接受 token 并继续自回归，因此不放松接受条件时输出序列与标准解码一致。速度提升取决于目标验证延迟、草稿长度 D 和接受长度 AL；若注意力主导解码时间，建议取 D=128/G−1，其中 G 是每个 KV 头共享的查询头数。当 G×\(1+D\) 落在 kernel tile 边界之间时会造成 tile 利用率下降，因此建议优先选使 G×\(1+D\) 为 128 倍数的草稿长度。文章还指出，在极低延迟区域，只有 AL 增量足以抵消草稿开销时才应增大 D；在 MoE 和长上下文等低并发场景下，较大的 D 有助于将 GEMM 推入计算受限区。

rss · NVIDIA Developer Blog · 9月2日 16:04

**「背景」** LLM 推理的解码阶段通常是逐个 token 自回归生成，每个 token 都需要读取模型权重，算术强度低、容易受内存带宽限制。投机解码先让小模型廉价生成若干候选 token，再由大模型并行验证，使单轮迭代产生多个 token，同时保持与标准解码一致的输出。

**「影响」** 对使用 NVIDIA GPU 优化 LLM 推理吞吐与延迟的开发者，这些准则提供了可按批量大小、注意力组大小和部署区域选择的草稿长度基准，可帮助在不大幅增加 KV cache 压力或并发度的情况下提升目标模型线性层的计算强度。速度增益最终仍依赖草稿模型的接受率和额外开销，实际效果会随模型和工作负载变化。

### [谷歌 Gemini 代理式视频分析：令牌消耗最多减少 88%](https://the-decoder.com/google-geminis-new-agent-based-video-analysis-cuts-token-usage-by-up-to-88-percent/) ⭐️ 7.0/10

谷歌为 Gemini Flash 系列模型推出基于代理的视频分析功能，使其不再按固定帧率逐帧扫描视频，而是自主决定分析哪些片段、以何种帧率和模态提取信息。谷歌表示，在处理长视频时该方式最多可节省 88% 的令牌、降低 66% 的成本，并提升准确性，可捕捉短于一秒的状态变化、剪辑切换，并准确统计重复动作和物体数量。该功能现已在 Gemini API 中提供，支持视频上传和 YouTube 视频，开发者只需将处理模式设置为“agentic”即可使用，无需额外费用，适用模型包括 Gemini 3.7 Flash、3.6 Flash 和 3.5 Flash-Lite。谷歌计划后续将该能力集成到 Gemini 应用以及 YouTube 的“Ask YouTube”功能中。

rss · The Decoder · 9月2日 08:21

**「背景」** 自 2025 年 Gemini 原生视频分析推出以来，系统一直采用静态处理方式，以默认每秒一帧的固定频率采样视频，并转录音频、逐帧分析，这导致长视频处理成本高昂或容易丢失关键细节。新的基于代理的分析方式将模型推理直接连接到原生视频工具，允许模型自行搜索相关片段、调整采样速度，并选择使用帧、音频还是转录文本，只加载任务所需的视频部分。此前开发者需要手动构建类似的选择性采样逻辑，而现在模型可以自主完成。

**「影响」** 该功能最直接惠及通过 Gemini API 分析较长视频（从 10 分钟教程到数小时录制内容）的开发者，使其无需自行构建选择性采样流程即可减少令牌消耗和成本，同时改善细节捕捉能力。不过相关效率和准确性数字来自谷歌自身的基准测试，实际收益仍需开发者针对具体任务验证。
